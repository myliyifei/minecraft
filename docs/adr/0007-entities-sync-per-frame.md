# 实体每帧全量同步，方块靠脏集重建

方块与实体在渲染层是两条完全不同的路。方块走脏集：核心记下「哪些格变过」，渲染层每帧取走这本账并重建过期的区块网格（`takeChangedBlocks` → `staleChunksFor`）。实体走全量遍历：渲染层每帧读一遍 `core.drops.all()`，按实体编号维护自己那批场景对象，新出现的建、消失的移除、留着的更新位置与姿态。

这条不对称来自两种东西的变化频率与代价正好相反。方块改动很少（挖一块、放一块），但一次改动要重建整个区块的网格——几千个面，几毫秒。实体每 tick 都在动，但每个只是一个小方块的位置与两个角度。把掉落物塞进区块网格，等于让它每落一格就重建一次区块；反过来，给方块也做「每帧全量遍历」则要每帧走一遍视距内几十万个格子。

实体的**表现**整个留在渲染层：核心只报位置、上一个 tick 的位置与存活 tick 数（`DropView`），漂浮的高度与旋转的角度由渲染层按 `age + alpha` 算。核心因此没有任何纯观感的状态，而相位在两次 tick 之间是连续的——20 tick/s 的相位放到 60fps 上要么一跳一跳，要么还得在渲染层再插值一次。

## Considered Options

- **把掉落物也画进区块网格**：省掉一套场景对象，代价是掉落物每动一格就要重建整个区块的网格。掉落物落地那几 tick 里每 tick 一次，一次几毫秒——一帧的预算就没了。
- **核心给渲染层发实体的增删事件**：渲染层只处理变化，不必每帧遍历。但核心得攒一份无界的事件日志等人来取（`takeChangedBlocks` 那笔账已经有这个问题，见 ADR-0006 的 Consequences，而实体的事件量级大得多）；而且渲染层每帧本来就要更新每个活着的实体的位置，遍历一遍并不比消费事件贵。
- **漂浮与旋转的相位存在核心里**：渲染层直接读现成的角度。代价是核心多了一份纯表现的状态，还会随 tick 以 20Hz 跳变；要平滑仍然得在渲染层插值，等于两头都做。

## Consequences

- 渲染层按 `DropView.id` 认实体，所以核心必须保证编号在一个实体活着的期间不变、且不复用已经消失的编号。
- 每帧的开销是 O(实体数)。掉落物是几个到几十个的量级，可以忽略；经验球（#9）与生物多起来时要重新看这条。
- 实体不进 `takeChangedBlocks()`，掉落物下落与被拾取因此一次网格重建都不触发（`tests/core/game.test.ts` 有一条守着）。
- 一个掉落物一个 `THREE.Mesh`，没有合并成 `InstancedMesh`：每个各自转、各自漂浮，合并省下的绘制调用换不回按物品分组、逐实例写矩阵的复杂度。连锁挖掘（#11）一次挖 64 块时再看。
- 经验球与生物照这条走：核心给「现有实体的列表 + 每个的位置与存活 tick」，渲染层自己维护场景对象。
