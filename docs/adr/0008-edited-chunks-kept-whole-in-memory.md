# 已改区块整块留在内存里，未改的丢掉重新生成

玩家挖开一个洞，走远到那个区块被卸载，再走回来——洞必须还在。地形生成是纯函数（ADR-0003），所以「重新加载就重新生成」对没动过的区块完全没问题，但对动过的区块等于把玩家的修改抹掉。

`World` 因此多了一张已改区块表：写进去的方块与原来不同的那一刻，这个区块进表；卸载只是把它从「已加载」里去掉，数据仍由那张表持有；重新加载时复用那一份，一次都不问区块来源。未改过的区块不进表，卸载即丢弃，回来时按种子重新生成，结果与上次一模一样。

留整块而不是只留那几处改动，是因为「复用」比「重新生成再补回改动」少一条接线：补回改动那条路上，区块从来源到手之后必须先重放改动、再交给任何读它的人（网格生成、碰撞、连锁挖掘的搜索），顺序错了就是一个只在走回头路时才出现的 bug。复用那一份还顺带省掉浏览器里的一趟 Worker：玩家走回来，那一格当场就在。

代价是内存随玩家的足迹只增不减，一个区块 96KB。本切片不落盘（spec #1 的 Out of Scope），内存是唯一的去处，而丢掉任何一个已改区块都等于丢掉玩家的修改，所以这张表不设上限。

## Considered Options

- **只留改动的日志**（区块内下标 → 方块），重新加载时按种子生成再重放。内存按改动条数计而不是按区块计，而且这正是将来落盘要写进存档的东西。但它要多一条「生成之后、交给别人之前重放改动」的接线，收益（内存）在不落盘的本切片里换不出来——真正需要它的是存档那一切片，那时再改这里。
- **给已改区块设上限，按最久未用丢弃**：内存有界，但丢掉的正是玩家的修改，与这条 ADR 要解决的问题是同一个。未取走的生成结果可以这么丢（见 `MAX_READY_CHUNKS`），因为那些还没人改过，重新生成一次就回来了。
- **卸载时立刻写进 IndexedDB**：内存问题一次解决，但存档、读档、多世界都在第一切片的范围之外。

## Consequences

- 已改区块永远不再经过区块来源。浏览器里因此走回头路不必等 Worker，也不存在「先看到没洞的地形、下一帧才改回来」的空档。
- 内存随足迹增长：改遍一千个区块是 96MB 的量级。存档那一切片要接手这件事——写盘之后就可以把已改区块从内存里放掉，或者干脆换成上面那条「只留改动」。
- 「算不算改过」与 `takeChangedBlocks()` 用的是同一条判定：写成原本就是的方块不算，所以对着石头放一块石头不会让那个区块从此赖在内存里。
- 已改区块不再重新生成，因此它不受地形生成算法变化的影响。一局游戏内算法不变，这条现在看不出来；将来有存档、而存档跨版本时，同一个世界里会出现「按新算法生成的地形」与「按旧算法生成、被改过因此留下来的地形」并存。
