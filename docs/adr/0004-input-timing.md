# 输入的时间性：移动意图跟 tick，视角即时生效

ADR-0002 说核心只认 tick，世界时间完全由 tick 数决定。读到这条再看见 `GameCore.turn()` 在 tick 之外直接改核心状态，很容易当成漏洞，所以把这条界线写下来：**改变持续状态的输入折成意图，等下一个 tick 生效；只决定"看向哪里"的输入立刻生效。** 键盘状态因此翻译成 `MoveIntent` 存在核心里，由 `step()` 在 tick 边界消费；鼠标移动则在事件里直接调 `turn()`。

这条不对称是有原因的，不是图省事。位置能在两个 tick 之间插值，因为渲染层手里有"上一个 tick"和"当前 tick"两个采样，中间那几帧插值出来就是平滑的（ADR-0002 说的就是这件事）。视角没有这个条件：如果它也只在 tick 边界变，渲染层要平滑就得朝当前那个采样追，于是瞄准比手上的鼠标慢半个到一个 tick——50ms 的瞄准延迟是第一人称里最容易被察觉的那种延迟。不追则更糟，60fps 下会连着三帧同一个角度，转头变成一格一格地跳。

ADR-0002 要守的确定性仍然成立：同一串 tick 加同一串输入得到同一个结果，因为视角和按键一样都是**输入**，本来就异步到达。核心测试自己调 `turn()` 与 `tick(n)`，因此完全可复现。

## Considered Options

- **把视角增量折进 `MoveIntent`，在 tick 里应用**：形式上最贴合 ADR-0002，但视角就只以 20Hz 变化，转头肉眼可见地卡顿。
- **视角仍跟 tick，由渲染层插值平滑**：画面是平滑的，代价是瞄准恒定落后最多一个 tick；而且 #7 的方块拾取要按视线投射，判定用的角度会和屏幕上看到的差一帧，准星指着的方块和实际挖到的方块可能不是一块。
- **把全部输入做成带时间戳的事件流，在 tick 内按到达顺序回放**：这是联机 lockstep 的做法，能让"同一串鼠标物理移动"在任何帧率下得到逐位相同的结果。本项目是单人、无回放需求（见 `docs/design-decisions.md`），这套机制的复杂度换不回对应价值。

## Consequences

- 核心状态可以在两个 tick 之间被输入改动。后续每个输入都要按这条线归类：挖掘的按下与松开、快捷栏切换、背包开合都改变持续状态，走意图；视线方向走即时。
- 同一串鼠标物理移动在不同帧率下走出的轨迹可能有微小差异——一个 tick 之前攒下几个 mousemove 取决于帧率。这不影响任何游戏规则，也不影响核心测试。
- 方块拾取（#7）读到的是即时视角，所以准星与判定始终指同一块方块。
- 灵敏度换算（像素 → 弧度）留在输入适配器里，核心只收弧度增量，并负责把俯仰夹在接近垂直的范围内。
