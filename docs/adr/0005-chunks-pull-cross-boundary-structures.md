# 跨区块的结构由每个区块自己拉取，而不是写进邻居

ADR-0003 定下地形生成是纯函数，并顺手给跨区块结构指了一条路：「按树根所在区块决定，允许写入相邻区块」。落地 issue #6（橡树生成）时这条走不通——生成一个区块的函数签名是 `(种子, 区块坐标) → 区块数据`，它手上只有一块内存，邻居区块此刻可能还没生成、可能已经卸载、也可能正在另一个 Worker 里。「写入相邻区块」得先有一个跨区块的可写世界，那正是 ADR-0003 要避免的东西。

改成反过来拉：每个区块自己扫一圈「树冠还能伸进来」的树格，把每一棵可能覆盖到自己的树都算出来，只写落在自己格子里的那部分。树的位置与形状仍然只由种子与树根坐标决定，所以两边算出的是同一棵树，合起来就是完整的一棵。

ADR-0003 的决定本身不变：生成不读相邻区块、不读已加载状态、同一个种子每次长出同一个世界。变的只是跨区块结构的实现手法。

## Considered Options

- **按 ADR-0003 原文写入相邻区块**：需要生成器持有一个跨区块的可写世界，结果重新依赖加载顺序与加载状态，等于放弃 ADR-0003 的决定。
- **生成完再补一遍「装饰」阶段**（原版的 feature 阶段那种做法）：要等四邻齐全才能装饰，于是区块有了「已生成但还没装饰」的中间态，流式加载与网格生成都得认这个状态。本切片不值当。

## Consequences

- 重叠的结构要有确定的先后。橡树按树格坐标字典序写，任何区块算出的相对顺序都一样，所以「谁盖住谁」是确定的。
- 同一棵树会被最多 4 个区块各算一遍。代价是每个区块多算十几个哈希，可以忽略。
- 结构的水平伸展范围必须是编译期已知的上界（橡树是 `OAK_CANOPY_RADIUS`），扫描范围才有得算。伸展范围不定的结构（大型洞穴系统）仍然要按 ADR-0003 Consequences 里那条「按确定性种子分区计算」另想办法。
