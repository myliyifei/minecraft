# 存档：核心只进出纯数据快照，已改区块整块压缩写进 IndexedDB

前五个切片不落盘，已改区块整块留在内存（ADR-0008），方块状态表随它常驻（ADR-0011），实体不随区块持久（ADR-0013），光照卸载即丢（ADR-0017）。这四篇都把「写盘之后怎么办」推给了存档切片。要定的有三件事：存在哪、已改区块以什么形态写、核心与存储的边界在哪。

定为：

- **核心只进出纯数据快照。** `GameCore` 多两个入口：导出一个快照，与从快照构造。快照是普通对象加 `Uint8Array`，不含函数与类实例。IndexedDB、压缩、文件导出导入、多标签页加锁都在核心之外的存储模块里。核心仍然不接触任何异步与非确定来源（架构测试里禁止 `localStorage` 那条照旧，IndexedDB 同样禁）。
- **已改区块整块写。** 每个已改区块一条记录，键是区块坐标，值是 96 KB 方块数组的 gzip（`CompressionStream`）。读回时直接放进已改区块表，不经过地形生成。光照与列顶高度不写，加载时重算（ADR-0017）。
- **存在 IndexedDB。** 一个数据库，世界元数据、玩家与实体、方块状态表、已改区块各一张表，按世界 id 分隔。
- **写盘后已改区块仍留在内存。** ADR-0008 的内存策略本切片不改，只多一个「上次写盘之后改过」的集合用于增量写。写盘后随普通区块一起卸载、走回来从 IndexedDB 异步读回，留给需要它的时候。

## Considered Options

- **localStorage**：单源 5 MB 上限，几十个已改区块就满。
- **OPFS**：文件语义适合整块二进制，但 Safari 与 Node 测试环境支持弱，只能在 Playwright 里测。IndexedDB 所有浏览器支持，可存 `ArrayBuffer`，Node 下有 fake-indexeddb。
- **只写改动日志（区块内下标 → 方块），加载时生成再重放**：体积最小，也是 ADR-0008 当初预想的方向。没有采用：`setBlock` 要新增逐方块的记录；已改区块从此也要经过 Worker，加载时多一处「生成之后、交给调用方之前重放」的顺序约束；而地形算法变了之后，在新地形上重放旧改动同样得不到正确结果，ADR-0008 指出的「新旧地形并存」问题它解决不了。整块 gzip 之后平原区块通常只有几 KB，体积上的差距不值这些代价。
- **核心直接持有存储接口，暂停时自己写**：核心从此有异步依赖，与固定 20 tick 的纯模拟模型（ADR-0002）冲突，单元测试也要带上假的存储。
- **写盘后立即释放内存**：实现 ADR-0008 当初的目标，但已改区块从「同步复用」变成「异步加载」，区块来源的接口、进入世界的加载路径、区块测试都要改，切片变大。一千个已改区块 96 MB 的上限实际很难碰到。

## Consequences

- 快照里除方块与状态之外，还要带 tick 计数、时刻偏移，以及掉落物、僵尸、经验球三个自增编号。它们是运行时随机（ADR-0014）的哈希输入，少存一个，同一存档重放的结果就不同。
- 快照只存持续状态：玩家的位置、视角、竖直速度、生命值与上次受伤的 tick、经验、背包与选中格；世界的 tick、时刻偏移、已改区块、方块状态表、掉落物与经验球。击退、落差、挖掘与攻击进度、排队输入、界面开合、光标物品、合成网格、僵尸、光照、粒子都是瞬态，不存。写盘前界面按关闭规则处理，光标物品退回。
- 存档带两个版本号：快照格式版本与地形算法版本。任一不同的世界在列表里标「版本不兼容」，只能删除或导出。本切片不写迁移代码，将来要迁移时再写。
- 物品与方块的数字编号从此真的进了存档：已发布的编号不可改、不可复用，只能追加。字符串枚举（工具类别、方块用途、状态种类、透光方式）仍不进存档，由编号查表重建。
- 增量写：已改区块只写上次写盘之后改过的；元数据、玩家、实体、方块状态表体积小，每次整体重写。
- 导出文件是自定的二进制容器：魔数、格式版本、JSON 元数据与玩家、实体、状态表，之后逐区块的 gzip 段。各段的编码与 IndexedDB 里的记录相同，导出就是把记录拼起来，导入就是拆开写回。扩展名 `.voxelworld`。
- 同一个世界用 Web Locks（`navigator.locks`）按世界 id 加锁，第二个标签页拿不到锁时不能进入。标签页关闭自动释放。
- ADR-0008 的「存档那一切片要接手内存释放」这一条没有在本切片完成，已在那篇补记。
- 和平难度与极限难度进了核心的构造参数：核心要知道难度才能决定生成与伤害。难度本身只在新建世界时定，随存档保存。
