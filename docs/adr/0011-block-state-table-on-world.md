# 方块的额外状态存在世界的一张按坐标索引的状态表里，不进区块数据，随已改区块常驻

熔炉（issue #30）是第一种带额外状态的方块：三个格子里的物品、燃料还能烧几 tick、原料炼了多少、成品积累的经验。区块数据是一格一个字节的 `Uint8Array`（ADR-0001、`Chunk`），只装得下方块种类，这些状态放不进去；而它们又必须跟着那一格走——玩家走远再回来，熔炉里的物品不能丢失。问题是「这一格的额外状态存在哪儿」。

定为：**世界持有一张方块状态表，键是世界坐标，值是那一格方块的额外状态。** 方块表多一列「方块状态」，记每种方块带哪一种状态（绝大多数是「无」）。`World.setBlock` 按这一列维护表：写下带状态的方块建一条空的，换成别的方块删掉那一条，同一种状态的两个编号之间切换（熄火与燃烧中的熔炉）那条不动。挖掘在把方块写成空气之前读一次状态，把里面装着的物品与方块自己的掉落一起在原位生成掉落物。区块卸载不删表里的条目：带状态的方块一定是玩家放的，那个区块因此是已改区块，整块留在内存里（ADR-0008），走回来时方块与状态都在。

选世界上的一张表而不是放进区块，是因为区块数据的形状是为网格生成与 Worker 传输定的：一格一字节、整块转移。往里加一列稀疏的对象，Worker 那一侧的生成、转移、`ChunkView` 直读内存的那几条每帧要走几十万次的路径全都要跟着变，而带状态的方块整个世界里也就几十个。按坐标索引一张表，两边互不影响：区块仍是一块纯内存，状态表只在放下、挖掉、点火那几处被读写。

## Considered Options

- **状态存进区块对象**（`Chunk` 多一张局部坐标到状态的表）：卸载与复用跟着区块走，不必另想。但 Worker 生成的区块是转移过来的一块 `ArrayBuffer`，主线程用它构造 `Chunk`；状态表得在主线程另建、卸载时随区块一起留在已改区块表里——与「世界上一张表」做的事一样，只是多了一层「先找到区块再找到格」。而且区块不知道方块表，「放下熔炉要建状态」这条规则得由世界告诉它。
- **状态是一种实体**（像掉落物那样由世界的实体列表持有、记着自己在哪一格）：实体每帧同步到渲染层（ADR-0007），而状态不需要画；实体会动、会消失，状态与方块同生同灭。把它做成实体是套用一套不适合它的生命周期。
- **把状态编码进方块编号**（每一种内容组合一个编号）：原料、燃料、成品三格各几十种物品、进度几百个 tick，组合数远超一个字节。「燃烧中」这一个布尔才值得占一个编号——那是贴图要不同，不是状态。

## Consequences

- 加一种带状态的方块（箱子）：方块表那一列填一个新种类，`block-state.ts` 加一种状态形状与它的初始值，`World.setBlock` 不改。
- 「换编号不换状态」让点火、熄火（#34）只是一次 `setBlock`：熔炉里的东西与进度都在原来那一条上。
- 挖掉带状态的方块时里面的物品一律掉出，不看工具：空手挖熔炉拿不到熔炉，原料、燃料、成品照样掉——物品不能凭空消失。
- 状态表只在 `setBlock` 里维护，所以凡是绕过 `setBlock` 改区块内存的地方（没有这样的地方；地形生成不生成熔炉）都会让两边对不上。将来地形生成要放带状态的方块（结构里的箱子）时，得在区块进世界那一步补建状态。
- 存档那一切片要把这张表与已改区块一起写盘；表按坐标索引，正好就是存档里「方块实体」那一段的形状。
