# 存档：核心只进出纯数据快照，已改区块整块压缩写进 IndexedDB

前五个切片不落盘，已改区块整块留在内存（ADR-0008），方块状态表随它常驻（ADR-0011），实体不随区块持久（ADR-0013），光照卸载即丢（ADR-0017），耐久随物品堆（ADR-0010）。这几篇都把「写盘之后怎么办」推给了存档切片。要定的有三件事：存在哪、已改区块以什么形态写、核心与存储的边界在哪。

定为：

- **核心只进出纯数据快照。** `GameCore` 多两个入口：导出一个快照，与从快照构造。快照是普通对象加 `Uint8Array`，不含函数与类实例。IndexedDB、压缩、文件导出导入、多标签页加锁都在核心之外的存储模块里。核心仍然不接触任何异步与非确定来源：架构测试里禁止 `localStorage` 那条照旧，本切片在同一条禁用表里新增 `indexedDB`。
- **已改区块整块写。** 每个已改区块一条记录，键是区块坐标，值是 96 KB 方块数组的 gzip（`CompressionStream`）。读回时直接放进已改区块表，不经过地形生成。光照与列顶高度不写，加载时重算（ADR-0017）。
- **存在 IndexedDB。** 一个数据库，世界元数据、玩家与实体、方块状态表、已改区块各一张表，按世界 id 分隔。
- **写盘后已改区块仍留在内存。** ADR-0008 的内存策略本切片不改，只多一个「上次写盘之后改过的区块」集合用于增量写。写盘后随普通区块一起卸载、走回来从 IndexedDB 异步读回，留给需要它的时候。

## Considered Options

- **localStorage**：单源 5 MB 上限，几十个已改区块就满。
- **OPFS**：文件语义适合整块二进制，但 Safari 与 Node 测试环境支持弱，只能在 Playwright 里测。IndexedDB 所有浏览器支持，可存 `ArrayBuffer`，Node 下有 fake-indexeddb。
- **只写改动日志（区块内下标 → 方块），加载时生成再重放**：体积最小，也是 ADR-0008 当初预想的方向。没有采用：`setBlock` 要新增逐方块的记录；已改区块从此也要经过 Worker，加载时多一处「生成之后、交给调用方之前重放」的顺序约束；而地形算法变了之后，在新地形上重放旧改动同样得不到正确结果，ADR-0008 指出的「新旧地形并存」问题它解决不了。整块 gzip 之后平原区块通常只有几 KB，体积上的差距不值这些代价。
- **核心直接持有存储接口，暂停时自己写**：核心从此有异步依赖，与固定 20 tick 的纯模拟模型（ADR-0002）冲突，单元测试也要带上假的存储。
- **写盘后立即释放内存**：实现 ADR-0008 当初的目标，但已改区块从「同步复用」变成「异步加载」，区块来源的接口、进入世界的加载路径、区块测试都要改，切片变大。一千个已改区块 96 MB 的上限实际很难碰到。

## Consequences

- 快照存世界的持续状态：种子、难度、极限已死亡标记、tick 计数、时刻偏移、首次出生点，掉落物、僵尸、经验球三个自增编号，已改区块、方块状态表、掉落物与经验球。tick 计数与三个自增编号是运行时随机（ADR-0014）的哈希输入；时刻偏移决定昼夜与天光减量，从而决定僵尸的生成与燃烧。少存其中任何一项，同一存档往后推进的结果就不同。
- 首次出生点要存：原点区块没加载又没改过时，重生点就是它（`GameCore.spawnPoint`）。读档时玩家可能远离原点，加载画面只等玩家周围的区块，构造时原点那一列可能还没加载，按「未加载即空气」算出来的出生点是错的。
- 快照存玩家的持续状态：位置、视角、竖直速度、落差、击退、生命值与上次受伤的 tick、经验、背包与选中格。落差与击退会影响之后几个 tick 的伤害与位置，在半空中暂停后读档不能让这次摔落的伤害消失。无敌时间不另存，由上次受伤的 tick 重建。
- 掉落物逐个存编号、物品堆（含耐久，ADR-0010）、位置、三轴速度、存活 tick 数；经验球逐个存编号、经验量、位置、速度、存活 tick 数。上一 tick 的位置只给渲染插值用，不存，恢复时取当前位置。
- 不存的瞬态：挖掘与攻击进度、排队输入、僵尸、光照、粒子。僵尸退出世界即消失，进入时按生成规则重新出现。
- 界面开合、光标物品与合成网格也不存。核心多一个立即生效的「关闭全部界面」指令，规则与按背包键关闭相同：光标物品退回原格，合成网格里的退回背包，放不下的掉在玩家脚下。取快照前与页面隐藏时都先调它。它与重生一样是 ADR-0004「输入等 tick 边界生效」的例外：暂停之后不再有 tick，排队的开合不会生效。
- 存档带两个版本号：快照格式版本与地形算法版本。任一不同的世界在列表里标「版本不兼容」，只能删除或导出。本切片不写迁移代码，将来要迁移时再写。
- 物品与方块的数字编号从此真的进了存档：已发布的编号不可改、不可复用，只能追加。字符串枚举（工具类别、方块用途、状态种类、透光方式）不进存档，由编号查表重建。方块状态表的记录因此去掉 `kind` 字段，读回时按那一格的方块编号查 `blockStateKind` 补回。
- 增量写：已改区块只写上次写盘之后改过的；元数据、玩家、实体、方块状态表体积小，每次整体重写。快照只复制本次要写的已改区块，不复制全部，取快照的同步耗时因此与改过的区块数成正比，而不是与已改区块总数成正比。
- 一次写盘的四张表在同一个 IndexedDB 读写事务里提交：gzip 全部完成之后才开事务，事务内不等待 IndexedDB 以外的 Promise，否则事务会提前自动提交。写失败（包括配额不足）时整次回滚，本次的「改过的区块」放回集合，下次写盘再写，暂停菜单提示写盘失败。
- 导出文件是自定的二进制容器：魔数、格式版本、JSON 元数据与玩家、实体、状态表，之后逐区块的 gzip 段，整数一律小端序。各段的编码与 IndexedDB 里的记录相同，导出就是把记录拼起来，导入就是拆开写回。扩展名 `.voxelworld`。导入的文件是不可信输入：除魔数与版本外，还要校验区块数与各段长度的上限、每段解压后正好是一个区块的字节数（解压时超出就中止）、方块与物品编号在已知范围内、JSON 字段的类型与取值范围，任一不符整份拒绝，不写入任何记录。
- 同一个世界用 Web Locks（`navigator.locks`）按世界 id 加锁。进入、删除、导出都先取锁，拿不到时提示「已在另一个标签页打开」，不执行。否则另一个标签页的增量写会在被删的世界里重新写出一份不完整的存档。标签页关闭自动释放。`navigator.locks` 与 `crypto.randomUUID` 只在安全上下文（localhost 或 https）可用，开发与 Windows 浏览器访问都走 localhost。
- ADR-0008 的「存档那一切片要接手内存释放」这一条没有在本切片完成，已在那篇补记。ADR-0010、0011、0013、0017 推迟到存档切片的事项按上面各条落实，已在各篇补记。
- 难度进了核心的构造参数：和平决定生成与已有僵尸的去留，各档决定僵尸的伤害，极限决定死亡画面。难度本身只在新建世界时定，随存档保存。
- 2026-10-03 补记（#64）：快照往返后的逐 tick 一致只保证到视距以内。流式加载在视距以内加载、卸载线多留 `UNLOAD_MARGIN` 环，玩家跨过区块边界后，原来的核心里视距外那一环还留着一些区块，从快照构造的核心只加载视距以内，那一环里的熔炉与掉落物因此暂停到玩家走近，规则与没加载的区块相同（ADR-0013）。快照不记已加载区块的坐标：浏览器里区块由 Worker 异步送来，那一环本来就不按 tick 复现。
- 2026-10-04 补记（#70）：导出文件的魔数是 ASCII 的 `VOXWORLD`。文件头的格式版本取元数据里的快照格式版本，版本不兼容的世界导出时写的是它自己的旧版本；导入要求文件头与元数据里的两个版本都与当前相同。导入的上限：区块数 4096（已改区块常驻内存，再多进入后内存不够用）、JSON 段 16 MB、每段 gzip 一个区块加 1 KB（不可压缩的数据经 deflate 存储块只多几十字节）；导出时按同样的上限查，超过的不导出，导出的文件都能再导入。JSON 段里每个对象的键要正好是快照的那几个，多一个也拒绝：校验通过的对象原样写进 IndexedDB。数值的范围按核心能接受的量级定，不只查有限：速度不超过下落的极限速度、计数器不超过 2⁴⁸、经验值不超过 2³¹ − 1，否则碰撞扫掠与等级换算在第一个 tick 就停不下来或要算很久。区块段在结构与 JSON 段查完之后逐个解压，查方块编号，并查带状态的方块与方块状态表一一对应；写回的仍是文件里的 gzip 字节。导入的世界名称与创建时间沿用文件里的，上次游玩时间取当前。
- 2026-10-04 补记（#71）：写盘时已改区块在压缩 Worker 里 gzip（`src/worker/gzip-worker.ts`），主线程一侧是 `createGzipClient`，经 `WorldStorageOptions.gzip` 交给存储模块；Node 下的测试默认直接调 `gzipChunk`。方块数组是取快照时复制出来的，转移给 Worker，不再复制。区块一个压完再压下一个；事务里区块的写每 100 个一批（`CHUNK_PUT_BATCH`），一批写成功才发下一批，等的是 IndexedDB 自己的请求，事务不会提前提交。原因是 Windows Edge 上 1000 个已改区块首次全量写盘的实测：原来所有区块一起开始压缩，1000 次把方块数组复制进 Blob 都在暂停的那一帧里，这一帧 276 ms，之后还有 95 ms 的帧；改成在主线程上逐个压，最长帧仍比不写盘时长 1 到 5 ms，因为 `CompressionStream` 在调用它的线程上压；同一个任务里发出 1000 个写，那一帧也多 5 到 8 ms。改完之后写盘期间除取快照那一帧外，最长帧与不写盘时相同，数据记在 #71。解压仍在主线程：读档时显示加载画面，导入时在世界列表上，都没有要画的世界。四张表名为 `worlds`、`states`、`blockStates`、`chunks`，世界锁的名称就是世界 id。
- 2026-10-05 补记（第七切片，ADR-0021）：`TERRAIN_VERSION` 改为 2。首次出生点不再是原点那一列，而是按种子算出的出生列；上面「原点区块没加载又没改过时，重生点就是它」改为出生列所在的区块，核心记住出生列，重生时加载的是它所在的区块。快照格式版本不变：新方块只是新的编号，物品编号照旧只追加。
- 2026-10-05 补记（#84）：首次出生点的算法。新建世界时核心从地形对象取出生列，以出生列所在的区块为中心按视距流式加载，再取出生列最高的实心方块，站在它的顶面中心，存为首次出生点；火把、水这类不实心的方块往下跳过。浏览器里加载画面在构造核心之前就等出生列所在区块周围半径 2 的区块（`SPAWN_READY_RADIUS`），构造时出生列已经有地形。读档不重算，首次出生点取快照里的。出生列所在区块没加载又没改过时，重生点就是首次出生点；改过又卸载了，重生时先把它放回世界，再按改过之后的方块重算。出生列总是列顶不是水的列，只有 1024 格以内一列陆地都没有、退回原点时列顶才可能是水，那时出生点落在水底的实心方块上。
