# 游戏核心以固定 20 tick/s 推进，渲染层不参与逻辑

挖掘计时、方块硬度、掉落物存活时间、连锁挖掘的进度这些规则都要能被测试精确断言，如果逻辑跟着帧率跑，同一段操作在 144Hz 和 30Hz 下会得到不同结果，测试也只能靠真实时钟等待。因此核心只认 tick：`tick(n)` 推进 n 步，世界时间完全由 tick 数决定，与真实时钟无关；浏览器侧的循环用累加器把真实时间换成整数个 tick，一帧内最多补 5 个，落后太多就丢弃欠账。视觉平滑由渲染层在两次 tick 之间插值负责。20 tick/s 与原版一致，硬度表可以直接照抄。

## Considered Options

- **逻辑跟随 requestAnimationFrame**：写起来最省事，但规则与帧率耦合，掉帧会改变游戏结果，测试必须依赖真实时钟。
- **更高的 tick 频率（如 60）**：手感差别不大，但硬度表要重算，且每 tick 的预算被压到 16ms 以内。

## Consequences

- 测试用 `tick(n)` 表达时间，不用 `setTimeout`，核心层测试因此是确定性的、毫秒级的。
- 渲染层拿到的是 tick 边界上的状态，移动、掉落物这些连续量需要插值，否则画面会以 20Hz 抖动。
- 后台标签页回到前台时会跳过时间而不是追赶，长时间挂机不等于长时间游戏内时间。
