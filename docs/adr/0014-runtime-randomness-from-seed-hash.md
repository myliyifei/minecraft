# 运行时随机也用种子哈希，核心不持随机状态

ADR-0003 把地形生成写成 `(种子, 区块坐标) → 区块数据` 的纯函数：地形、树、矿脉里的随机都由 `hashCoords(种子 ^ 盐, 坐标…)` 算出来，同一个种子不论加载顺序如何都得到同一个世界。实体进来之后，推进过程中也要随机：掉落物散开的初速度、僵尸游走的方向、僵尸死亡时掉几件腐肉、僵尸在哪一列自然生成。问题是这些随机从哪里来。

定为：**运行时随机同样用种子哈希算出来，核心不持随机状态。** 每一处随机各取一个盐，与种子异或之后，再把这一次随机「属于谁、发生在哪一 tick」作为哈希的输入：

- 游走的方向：`hashCoords(种子 ^ WANDER_SALT, tick, 僵尸编号)`。
- 腐肉的件数：`hashCoords(种子 ^ LOOT_SALT, tick, 僵尸编号)`。
- 自然生成的候选列：`hashCoords(种子 ^ SPAWN_SALT, tick, 0)` 给角度，`(…, tick, 1)` 给距离。
- 掉落物散开的初速度：由种子、所在方块坐标与掉落物编号哈希出来（`drop.ts`）。

tick 用核心的 tick 计数，不用世界时刻：`setTimeOfDay` 只改时刻相对 tick 计数的偏移，拨时刻不改哈希的输入。编号自增、不复用，同一 tick 里的几只因此各有各的值。`Math.random`、`Date.now` 仍被架构测试禁止在核心里出现。

这样同一种子、同一串指令每次得到同样的实体：生成的位置与 tick、游走的轨迹、掉落的件数逐一相同，测试可以直接断言「两次运行 3000 tick 后僵尸列表逐字段相同」。

## 为什么不用带种子的伪随机数生成器

一个由种子初始化、每用一次往前走一步的生成器也是确定性的，但它的每个输出取决于在它之前一共取过几次。于是某一处随机的结果与其他所有取随机的地方耦合：

- 僵尸在区块边上原地等一 tick、这一 tick 没选方向，之后所有僵尸的游走、所有腐肉件数都换了一组值。
- 玩家头顶盖一层方块，如果某一步因此少取或多取一次，之后的生成位置就全变了。按哈希算时，候选列只取决于种子、tick 与玩家的位置，测试直接断言盖不盖方块生成结果都一样。
- 以后加一种生物或一处新的随机，取随机的次序变了，已有的测试期望值也随之全部改变。

按哈希算时，每一处随机只看自己的输入，彼此独立，增删一处不影响其他各处。

## Considered Options

- **带种子的伪随机数生成器**：理由见上一节。
- **`Math.random`**：同一种子两次运行结果不同，确定性的测试无法编写，同一种子不再对应同一局游戏。
- **每只实体各持一个生成器**：各只之间不再互相影响，但同一只内部仍有次序耦合（游走少取一次，掉落件数就变），而且生成器的状态要跟着实体保存。

## Consequences

- 生成失败不重试：候选列不满足条件（区块没加载、列顶不是实心、离玩家太近或太远）时，这一 tick 就放弃。要重试得再算一个哈希输入，下一次尝试是 20 tick 之后，没有必要。
- 哈希的输入必须本身是确定的：tick 计数、编号、方块坐标都是；实体在数组里的下标不作为输入：它随别的实体移除而变，一只实体的随机就又和别的实体有了关联。
- 每一处随机要有自己的盐。两处共用同一组 `(种子, tick, 编号)` 而不加盐，两个结果就来自同一个哈希值，互相关联：同一 tick、同一只僵尸的游走方向与腐肉件数就不再独立。
- 这是 ADR-0003 纯函数原则从地形到实体的延伸：地形是 `(种子, 坐标)` 的函数，实体的随机是 `(种子, tick, 编号)` 的函数，核心里仍然没有随机状态。
