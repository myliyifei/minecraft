# 目标方块每 tick 算一次，渲染层不自己投射视线

挖掘、放置、连锁挖掘都要先回答「玩家对着哪一块」。这条射线在核心的 `step()` 里每 tick 投一次，结果存成目标方块（含命中面）；渲染层画选框与裂纹时读的就是它，不另投一条。

选这条是为了让**判定与画面不可能分叉**。如果渲染层每帧自己投一条射线来画选框，屏幕上框住的方块和这一 tick 真正挖到的方块就是两次独立计算的结果——转视角的那几帧里它们会指向不同的方块，玩家看到框在 A 上、碎的却是 B。共用核心那一个答案，这种情形在结构上就不存在。

代价是选框最多滞后一个 tick（50ms）：视角是即时的（ADR-0004），而目标只在 tick 边界更新，快速转视角时框会追一下才跟上。这跟 ADR-0004 拒绝的那种延迟不是一回事——那条说的是**瞄准输入**不能延迟（视角本身必须即时生效，否则手感是黏的），这里延迟的只是选框这个反馈的刷新率，而且它与判定始终一致。

ADR-0004 里那句「准星与判定始终指同一块方块」因此要读成：**选框与判定**始终一致。屏幕正中央与判定之间可以差最多一个 tick 的转角。

## Considered Options

- **渲染层每帧自己投一条射线画选框**：选框跟手，代价是判定与画面成了两份计算，转视角时会分叉——这正是 ADR-0004 想避免的那种「框着一块、挖到另一块」。
- **核心每帧被渲染层调一次「重新瞄准」**：选框既跟手又只有一份答案，但核心状态就随帧率变化了，20 tick/s 的确定性（ADR-0002）没了，挖掘计时也不再能靠 tick 数精确断言。
- **目标由输入事件驱动更新（鼠标一动就重投）**：视角即时生效，目标也即时。核心状态会在 tick 之外被改，与 ADR-0004 的分类不冲突，但每次 mousemove 投一条射线是每 tick 好几次的浪费，换回来的只是选框早 50ms 跟上。

## Consequences

- 触及距离与射线检测都是核心的东西（`PLAYER_REACH`、`raycastBlocks`），放置（#10）与连锁挖掘（#11）直接复用同一个目标，不各自再投一条。
- 渲染层不需要知道触及距离、也不需要会投射线，只需要「目标方块坐标 + 进度」这两个值（方块是个单位立方体这件事它本来就知道，网格生成靠的就是它）。裂纹分几阶因此完全是贴图的事（`crackStage`）。
- 挖穿一块之后核心当场重投一次射线，目标同一 tick 内就落到后面那块上——否则选框会在一个 tick 里套着一个已经不存在的方块。
