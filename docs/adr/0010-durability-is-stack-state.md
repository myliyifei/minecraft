# 耐久是格子里那一堆的状态，不是独立实体

工具（issue #22）要有耐久：每挖穿一块损耗 1 点，损耗到满工具消失；界面上要画剩余比例。问题是「这把镐剩多少耐久」存在哪儿。

定为：**耐久记在格子里那一堆物品上。** `ItemStack` 多一个可选字段 `damage`（已损耗几点），只在工具上出现，没有这个字段就是满耐久。满耐久是多少由材质档决定（物品表的 `TOOL_MATERIALS`），剩余耐久是两者的差，不单独存。挖掘那一步挖穿之后让选中格里那一堆损耗几点（`Inventory.wearHeld`），损耗到满那一格清空——这条规则是物品层的一个纯函数（`wornTool`），背包只是把结果写回格子。

选「堆的状态」而不是给每把工具一个实体，是因为这个游戏里物品本来就是按格子里的堆存的，没有「物品实例」这一层：格子里是 `{ 物品种类, 数量 }`，背包、合成网格、掉落物、光标物品之间移动的都是这个。工具的堆叠上限是 1，所以一堆就是一把，把损耗写在堆上正好一一对应，而且移动物品的每一条路（拿起放下、归还、入包、拾取）都不必知道「这是一把工具」——它们移动的还是同一堆。代价是这些路上凡是「从一堆里分出一部分」的地方都不能再手写 `{ item, count }`，得用 `withCount` 沿用原堆的其余字段，否则一把旧镐归还一次就成了新的。

## Considered Options

- **每把工具是一个带编号的实体，格子里存编号**：实例可以带任意状态（附魔、命名），但要多一张实体表、一套编号分配与回收，而且格子里的东西从此有两种形状（堆与引用），拿起放下、合成、掉落物全都得分两条路。本切片只有耐久这一个状态，用不上这一层；附魔在明确排除的范围里。
- **耐久存在选中格之外的「手上那把工具」对象里**：挖掘读写都方便，但换选中格、把工具放进储物格时得跟着移过去，两把镐互换位置时更要分清每份耐久属于哪一把——正是「状态与它描述的东西分离」那类 bug 的来源。
- **把损耗算进数量：一把满耐久的镐是 59 个，挖一块少 1 个**：数据上不用加字段，但数量标签会显示「59」，堆叠、合并、配方书数材料全都要为工具开特例。

## Consequences

- `ItemStack` 有了一个可选字段，所有测试里 `toEqual({ item, count })` 对满耐久的工具与材料仍然成立，对用过的工具要写上 `damage`。
- 凡是从一堆里分出一部分的代码走 `withCount`：背包入包、界面归还与合并、网格消耗、掉落物被拾走一部分。新加一条移动物品的路径时同样如此。
- 掉落物存的是整堆而不是拆开的种类与数量，关闭界面时掉在脚下的旧镐拾回来仍是旧的。
- 石制工具（#23）只加一行材质档数据；连锁挖掘按块数一次结算损耗，超过剩余耐久时方块照样全碎、工具随后消失，那条规则也在 `wornTool` 里。
- 剑（#45）进来之后，挖穿一块损耗几点改为按工具类别查（`miningWearOf`：镐斧铲 1、剑 2），攻击一下损耗几点同样按类别查（`attackWearOf`：剑 1、镐斧铲 2）。上文「每挖穿一块损耗 1 点」是 #22 时的需求。两张表只决定损耗几点，损耗仍记在那一堆上，本决定不变。
- 将来的存档把 `damage` 随格子一起写盘即可，不另存工具表。
