# 输入的时间性：移动意图跟 tick，视角即时生效

ADR-0002 说核心只认 tick，世界时间完全由 tick 数决定。读到这条再看见 `GameCore.turn()` 在 tick 之外直接改核心状态，很容易当成漏洞，所以把这条界线写下来：**改变持续状态的输入转换成意图，等下一个 tick 生效；只决定「看向哪里」的输入立刻生效。** 键盘状态因此翻译成 `MoveIntent` 存在核心里，由 `step()` 在 tick 边界消费；鼠标移动则在事件里直接调 `turn()`。

这条不对称有具体原因。位置能在两个 tick 之间插值，因为渲染层持有「上一个 tick」和「当前 tick」两个采样，中间那几帧插值出来就是平滑的（ADR-0002 说的就是这件事）。视角没有这个条件：如果它也只在 tick 边界变，渲染层要平滑就得向当前那个采样逼近，于是瞄准比手上的鼠标慢半个到一个 tick——50ms 的瞄准延迟是第一人称里最容易被察觉的那种延迟。不逼近则更糟，60fps 下会连着三帧同一个角度，转头变成一格一格地跳。

ADR-0002 要守的确定性仍然成立：同一串 tick 加同一串输入得到同一个结果，因为视角和按键一样都是**输入**，本来就异步到达。核心测试自己调 `turn()` 与 `tick(n)`，因此完全可复现。

## Considered Options

- **把视角增量并入 `MoveIntent`，在 tick 里应用**：形式上最贴合 ADR-0002，但视角就只以 20Hz 变化，转头肉眼可见地卡顿。
- **视角仍跟 tick，由渲染层插值平滑**：画面是平滑的，代价是瞄准恒定落后最多一个 tick；而且 #7 的目标方块判定要按视线投射，判定用的角度会和屏幕上看到的差一帧，准星指着的方块和实际挖到的方块可能不是一块。
- **把全部输入做成带时间戳的事件流，在 tick 内按到达顺序回放**：这是联机 lockstep 的做法，能让「同一串鼠标物理移动」在任何帧率下得到逐位相同的结果。本项目是单人、无回放需求（见 `docs/design-decisions.md`），这套机制很复杂，而本项目从中得不到相应的好处。

## Consequences

- 核心状态可以在两个 tick 之间被输入改动。后续每个输入都要按这条线归类：挖掘的按下与松开、快捷栏切换、背包开合都改变持续状态，走意图；视线方向走即时。
- 同一串鼠标物理移动在不同帧率下走出的轨迹可能有微小差异——一个 tick 之前积累几个 mousemove 取决于帧率。这不影响任何游戏规则，也不影响核心测试。
- 目标方块判定（#7）读到的是即时视角，不是插值过的视角。
  > 「准星与判定始终指同一块方块」这句在实现 issue #7 时由 ADR-0006 作了更细的界定：目标方块每
  > tick 算一次，选框画的就是它，所以**选框与判定**始终一致；屏幕正中央与判定之间可以差
  > 最多一个 tick 的转角。上面这个决定本身不变。
- 灵敏度换算（像素 → 弧度）留在输入适配器里，核心只收弧度增量，并负责把俯仰夹在接近垂直的范围内。
- 重生（#40）是改变持续状态的输入，但不走意图，按下重生按钮当场生效。死亡画面期间输入层每帧释放指针锁定（`PlayerControls.sync`），而锁定只能在按钮的 click 里抓回。重生若等到下一个 tick，这一帧里死亡画面还在，刚抓回的锁定会被当场释放，之后就没有用户手势再抓它了。重生只在死亡画面上发生，这时世界里没有玩家的其他输入可以与它排先后，立即生效不影响确定性。
- 2026-10-03 补记（第六切片，ADR-0018、ADR-0019）：「关闭全部界面」是第二个立即生效的例外。取快照前与页面隐藏时要关掉开着的界面、退回光标物品，而暂停之后不再有 tick，按背包键那条排队的路不会生效。
